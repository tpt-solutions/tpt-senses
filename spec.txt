**Repository:** `tpt-senses`
**Organisation:** TPT Solutions
**Language:** Rust
**License:** MIT
**Status:** Design Specification
**Version:** 0.1.0

---

# 1. Purpose

`tpt-senses` is a general-purpose Rust sensory and perception foundation for TPT's cognitive, robotic, autonomous, and intelligent systems.

It provides a common abstraction for acquiring, representing, processing, correlating, and delivering observations about:

* the external world
* the system's physical body
* the system's environment
* other entities
* internal system state
* simulated environments

`tpt-senses` is **not** intended to replace:

* hardware drivers
* ROS / ROS 2
* camera frameworks
* audio codecs
* computer-vision algorithms
* robotics middleware
* individual sensor SDKs

Instead, it provides the abstraction layer above those systems.

The central principle is:

> **Sensors produce measurements. Perception produces observations. Cognition reasons about observations.**

---

# 2. Problem

The TPT cognitive architecture is increasingly capable of reasoning, reflection, memory, planning, verification, and autonomous action.

However, the architecture requires a general mechanism for receiving information about reality.

Currently, sensor capabilities are fragmented across domain-specific systems:

```text
camera
microphone
LiDAR
GPS
IMU
ROS
computer vision
audio processing
robotics
IoT
industrial sensors
etc.
```

These systems expose raw or semi-processed data but do not provide a unified cognitive sensory model.

A cognitive system should not need to understand whether an observation originated from:

* a camera
* a LiDAR
* a microphone
* a radiation detector
* a ROS topic
* a simulation
* a database
* another AI
* an internal system monitor

It should receive a common representation of:

```text
what was observed
where
when
by what
with what confidence
under what conditions
and what the observation means
```

# 3. Core Principle

`tpt-senses` is based on a layered model:

```text
                  REALITY
                     │
                     ▼
               ┌───────────┐
               │  SENSOR   │
               └─────┬─────┘
                     │
                 measurement
                     │
                     ▼
               ┌───────────┐
               │ PERCEPTION│
               └─────┬─────┘
                     │
                 observation
                     │
                     ▼
               ┌───────────┐
               │ TPT-SENSES│
               └─────┬─────┘
                     │
              interpreted state
                     │
                     ▼
               ┌───────────┐
               │  COGNITION│
               │            │
               │ tpt-anima  │
               │ tpt-thought│
               │ tpt-eve    │
               └───────────┘
```

The architecture must preserve the distinction between **measurement** and **interpretation**.

For example:

```text
Measurement:

temperature = 83.4°C
```

is different from:

```text
Observation:

engine_component.temperature_state = abnormal
```

The first is sensor data.

The second is perception.

The cognitive layer can then reason:

```text
"Component 17 is overheating."
```

The system must not assume that intelligence has human-like senses.

Supported modalities should include, but not be limited to:

* vision
* hearing
* touch
* smell
* taste
* proprioception
* balance
* temperature
* pressure
* force
* torque
* vibration
* depth
* LiDAR
* radar
* infrared
* ultraviolet
* multispectral sensing
* hyperspectral sensing
* chemical sensing
* gas sensing
* radiation
* magnetic fields
* electric fields
* GPS/GNSS
* inertial measurement
* environmental sensors
* biological sensors
* industrial sensors
* simulated sensors

New modalities must be addable without changing the core architecture.

# 5. Non-Human Sensory Capabilities

The system must explicitly support sensory capabilities beyond human biological perception.

Examples:

```text
Human:
    visible light
    human auditory range
    pressure
    temperature
```

Potential machine:

```text
visible
infrared
ultraviolet
thermal
ultrasonic
infrasound
radio
LiDAR
radar
radiation
magnetic
electrical
chemical
```

The architecture must not encode assumptions such as:

```text
vision = human vision
hearing = human hearing
```

Instead:

```text
VisionCapability {
    spectral_range: ...
    spatial_resolution: ...
    temporal_resolution: ...
}
```

and:

```text
AuditoryCapability {
    frequency_range: ...
    dynamic_range: ...
    spatial_resolution: ...
}
```

This allows configurations resembling:

```text
human
eagle
rabbit
bat
industrial robot
drone
agricultural robot
spacecraft
custom machine
```

without requiring biological imitation.

These names should be treated as conceptual profiles rather than claims of biological equivalence.

# 8. ROS Integration

ROS / ROS 2 should be treated as an **integration layer**, not a dependency of the core crate.

Architecture:

```text
ROS
 │
 ├── camera topic
 ├── LiDAR topic
 ├── IMU topic
 ├── GPS topic
 ├── force topic
 └── custom sensor topic
       │
       ▼
ROS adapter
       │
       ▼
tpt-senses
```

The core `tpt-senses` crate must remain usable without ROS.

Potential future crates:

```text
tpt-senses
tpt-senses-ros
tpt-senses-ros2
```

These should only be created when justified by implementation complexity.

# 9. Sensor Model

The fundamental abstraction is a `Sensor`.

Conceptually:

```rust
trait Sensor {
    type Measurement;

    fn identity(&self) -> SensorId;

    fn capabilities(&self) -> &SensorCapabilities;

    fn read(&mut self) -> Result<Self::Measurement, SensorError>;
}
```

Sensors should expose:

* identity
* capabilities
* measurement type
* timestamp
* calibration state
* health state
* provenance
* uncertainty

---

# 10. Sensor Capabilities

A sensor should describe what it is capable of measuring.

Example:

```rust
struct SensorCapabilities {
    modalities: Vec<Modality>,
    sampling_rate: Option<Frequency>,
    spatial_resolution: Option<Resolution>,
    temporal_resolution: Option<Duration>,
    measurement_range: Option<Range>,
    spectral_range: Option<SpectralRange>,
}
```

Capabilities must be descriptive rather than tied to biological assumptions.

# 12. Measurement

A measurement represents raw or minimally processed sensor output.

Example:

```rust
struct Measurement {
    sensor: SensorId,
    modality: Modality,
    value: MeasurementValue,
    timestamp: Timestamp,
    uncertainty: Option<Uncertainty>,
    provenance: Provenance,
}
```

Possible values include:

```text
scalar
vector
matrix
image
audio buffer
point cloud
spectrum
categorical value
structured measurement
custom binary data
```

Large data should support zero-copy or streaming representations where practical.

---

# 13. Observation

An observation is a semantically meaningful interpretation of one or more measurements.

Example:

```rust
struct Observation {
    id: ObservationId,
    subject: Option<EntityId>,
    modality: Modality,
    property: Property,
    value: ObservationValue,
    confidence: Confidence,
    timestamp: Timestamp,
    location: Option<SpatialReference>,
    provenance: Provenance,
}
```

Example:

```text
subject:
    plant_1847

property:
    possible_disease

value:
    fungal_stress

confidence:
    0.87
```

---

# 14. Measurement vs Observation

This distinction is fundamental.

```text
MEASUREMENT

temperature = 37.4°C
```

becomes:

```text
OBSERVATION

object.temperature_state = normal
```

Multiple measurements may produce one observation:

```text
camera
+
thermal camera
+
LiDAR
+
spectral camera
+
GPS
       │
       ▼
    fusion
       │
       ▼
Observation:
    Plant #1847
    location = ...
    species = ...
    stress_probability = ...
```

---

# 15. Uncertainty

No sensor should be assumed to be perfectly accurate.

Every meaningful measurement/observation should support uncertainty.

Possible representations:

```rust
struct Uncertainty {
    confidence: Option<f64>,
    standard_deviation: Option<f64>,
    bounds: Option<(f64, f64)>,
    distribution: Option<Distribution>,
}
```

The architecture must distinguish:

```text
value
confidence
precision
accuracy
uncertainty
```

These are not interchangeable.

---

# 16. Provenance

Every observation should be traceable to its source.

Example:

```text
Observation
    ↓
Perception algorithm
    ↓
Measurement
    ↓
Sensor
    ↓
Hardware
```

Provenance should allow the system to answer:

> "Why do we believe this?"

Example:

```text
Observation:
    obstacle_detected

Sources:
    camera_02
    lidar_01

Algorithms:
    detector_v4
    fusion_v2

Timestamp:
    ...

Confidence:
    0.96
```

This is especially important for `tpt-eve`, verification, debugging, and reflection.

---

# 17. Temporal Model

Sensors operate at different frequencies.

Example:

```text
GPS:       10 Hz
LiDAR:     20 Hz
Camera:    60 Hz
IMU:       500 Hz
Thermal:   30 Hz
Chemical:  1 Hz
```

`tpt-senses` must support temporal alignment.

It should preserve:

* sensor timestamp
* acquisition timestamp
* processing timestamp
* observation timestamp
* latency
* ordering
* clock source

Never silently treat asynchronous measurements as simultaneous.

---

# 18. Spatial Model

Sensors may use different coordinate frames.

For example:

```text
world
  ↓
robot
  ↓
body
  ↓
camera
  ↓
pixel
```

`tpt-senses` should support spatial references without requiring a particular robotics framework.

Where available, it should integrate with external transform systems such as ROS TF.

---

# 19. Sensor Fusion

Sensor fusion is a major responsibility of `tpt-senses`.

Fusion combines multiple measurements into a more useful observation.

Example:

```text
Camera:
    object = vehicle
    confidence = 0.81

LiDAR:
    distance = 13.2m

Radar:
    velocity = 4.1m/s

GPS:
    position = ...

       ↓

FUSED OBSERVATION

Vehicle #27
position = ...
velocity = ...
distance = 13.2m
classification = vehicle
confidence = 0.94
```

Fusion must preserve the underlying evidence.

It must never erase provenance.

---

# 20. Entity Association

Multiple sensors may observe the same physical entity.

`tpt-senses` should support entity association:

```text
camera_01 → object A
lidar_01  → object B
radar_01  → object C
```

where:

```text
A ≈ B ≈ C
```

becomes:

```text
Entity #1042
```

The association itself should have confidence and provenance.

---

Events should contain:

* timestamp
* source
* affected entity
* modality
* measurements
* confidence

# 22. State

`tpt-senses` should support maintaining current sensory state.

Example:

```text
WORLD STATE

Robot:
    position
    orientation
    velocity

Nearby:
    vehicle_12
    person_8
    plant_1847

Environment:
    temperature
    humidity
    light
    radiation

Robot body:
    battery
    motor temperatures
    joint torque
```

State should be derived from observations rather than becoming an independent source of truth.

# 23. Internal Sensing

`tpt-senses` should support sensing the system itself.

This includes:

```text
battery level
CPU utilisation
GPU utilisation
memory pressure
temperature
motor temperature
joint position
joint torque
network quality
sensor health
actuator health
```

It may also provide interfaces for higher-level cognitive/internal observations such as:

```text
prediction error
uncertainty
contradiction
attention demand
goal conflict
```

However, cognitive state should remain owned by the appropriate cognitive repositories.

`tpt-senses` provides the observation mechanism, not the cognitive interpretation.

# 25. Biological Inspiration

Biological organisms may be useful reference models.

Examples:


# 26. Perception Pipeline

A standard perception pipeline should support:

```text
measurement
    ↓
validation
    ↓
calibration
    ↓
normalisation
    ↓
feature extraction
    ↓
classification
    ↓
entity association
    ↓
sensor fusion
    ↓
observation
    ↓
world state
```

Individual stages should be optional.

A simple sensor may provide:

```text
measurement → observation
```

while a complex vision pipeline may provide:

```text
image
 → detection
 → segmentation
 → tracking
 → classification
 → fusion
 → observation
```

---

# 27. Streaming

Sensors naturally produce streams.

`tpt-senses` should support:

```text
SensorStream<T>
```

with:

* backpressure
* buffering
* cancellation
* timestamps
* ordering
* dropped-sample reporting
* rate limiting
* filtering

The design should favour asynchronous Rust where appropriate.

---

# 28. Determinism

The architecture should support deterministic replay.

A recorded sensor stream should be replayable:

```text
recorded measurements
        ↓
tpt-senses
        ↓
same perception pipeline
        ↓
reproducible observations
```

This is important for:

* testing
* debugging
* simulation
* regression testing
* robotics development
* AI evaluation
* verification

---

# 29. Recording and Replay

Capabilities:


The core crate should not require a particular storage format.

# 30. Simulation

`tpt-senses` should work with simulated environments.

Example:

```text

    ↓
virtual sensors
    ↓
tpt-senses
    ↓
tpt-thought
```


# 31. Sensor Health

Sensors themselves are entities that require monitoring.

Support:

```text
Online
Offline
Degraded
Calibrating
Faulted
Unknown
```

Additional diagnostics:

```text
signal quality
noise
latency
drop rate
temperature
calibration status
```

A cognitive system should be able to reason:

```text
"Camera confidence is low because the lens is obstructed."
```

rather than merely receiving:

```text
object confidence = 0.31
```

# 32. Calibration

Calibration must be represented explicitly.

Examples:

```text
intrinsic calibration
extrinsic calibration
temperature calibration
zero-point calibration
time calibration
sensor alignment
```

Calibration state should be part of provenance.

# 33. Security and Trust

Sensor data may be untrusted.

The architecture should support:

```text
source identity
authentication status
integrity status
provenance
trust metadata
```

This becomes increasingly important when observations originate from:

* network devices
* external systems
* other agents
* remote robots
* third-party APIs

A sensor observation should not automatically become a fact.

# 34. Observation Lifecycle

A useful lifecycle is:

```text
RAW
  ↓
VALIDATED
  ↓
CALIBRATED
  ↓
PROCESSED
  ↓
CORRELATED
  ↓
OBSERVED
  ↓
FUSED
  ↓
CONSUMED
  ↓
ARCHIVED
```

Not every observation must pass through every stage.

# 35. Relationship With TPT-ANIMA

`tpt-anima` should manage cognitive state, attention, agency, memory-related processes, and other higher-level mechanisms.

`tpt-senses` supplies observations.

Example:

```text
tpt-senses
    │
    │ "movement detected"
    ▼
tpt-anima
    │
    │ attention allocation
    ▼
tpt-thought
```

This allows attention to influence sensing.

For example:

```text
normal:
    camera = low processing

interesting event:
    camera = increase resolution
    microphone = increase sampling
    LiDAR = increase frequency
```

This creates a potential future **active perception** system.

---

# 36. Active Perception

A major future capability should be active sensing.

Instead of:

```text
sense → think
```

the system can perform:

```text
sense
 ↓
uncertainty
 ↓
think
 ↓
request additional information
 ↓
sensor action
 ↓
new observation
```

Example:

```text
"Is that a weed?"

Camera confidence:
    0.61

Thought:
    insufficient evidence

Request:
    acquire multispectral image

New evidence:
    multispectral confidence = 0.94

Updated observation:
    likely weed
```

This is an important bridge between `tpt-senses` and autonomous cognition.

```text
  ↓
tpt-anima
  ↓
Attention
  ↓
tpt-thought
  ↓
Reasoning
  ↓
Decision
  ↓
Action
  ↓
WORLD
  ↓
New measurements
```

This creates the sensory half of the broader cognitive feedback loop.

---

# 46. Relationship With Thought, Reflection and Sleep

`tpt-thought` should be able to consume observations during active cognition.

Reflection can examine:

```text
What did I observe?
How reliable was it?
Was my interpretation correct?
What evidence contradicted it?
What predictions failed?
```

Sleep/offline processing can examine historical sensory data:

```text
sensory history
    ↓
pattern discovery
    ↓
memory consolidation
    ↓
model refinement
```

Therefore sensory data becomes part of the AI's experiential history without making `tpt-senses` responsible for memory.

---

# 47. Verification

Because TPT has a strong interest in verification, sensory transformations should be inspectable.

Where practical, each transformation should expose:

```text
input
algorithm/version
parameters
output
uncertainty
provenance
```

This enables questions such as:

```text
Which measurement produced this observation?

Which algorithm produced this classification?

Which sensors supported this conclusion?

What uncertainty existed?

What changed between versions?
```

This integrates naturally with `tpt-eve` and the wider verification architecture.

---

# 48. Testing Strategy

Testing must occur at multiple levels.

## Unit tests

Test:

* modality handling
* timestamps
* uncertainty
* provenance
* coordinate systems
* calibration
* observation construction
* event handling

## Integration tests

Test:

```text
sensor → measurement → observation
```

## Fusion tests

Test:

```text
sensor A + sensor B → fused observation
```

## Replay tests

Ensure recorded sensor streams produce deterministic results where the pipeline is designed to be deterministic.

## Fault tests

Simulate:

```text
missing sensors
bad timestamps
sensor noise
stale data
out-of-order messages
calibration failure
sensor disagreement
```

---

# 49. Safety

`tpt-senses` should never imply that an observation is necessarily true.

The architecture must preserve uncertainty.

For safety-critical systems:

```text
observation
    ≠
fact
```

and:

```text
high confidence
    ≠
certainty
```

Safety-critical decision-making should remain outside the sensory layer.

---

# 50. Performance

The implementation must support high-frequency sensor streams.

Important requirements:

* minimal allocation where practical
* zero-copy data where practical
* asynchronous streams
* bounded buffering
* configurable backpressure
* efficient timestamps
* efficient identifiers
* optional serialization
* no mandatory heavyweight dependencies

Large data such as:

```text
video
audio
point clouds
hyperspectral imagery
```

must not be unnecessarily copied simply to construct observations.

---

# 51. Embedded Compatibility

The architecture should remain compatible with constrained systems where practical.

Avoid making:

```text
std
heap allocation
threads
network access
```

mandatory for the foundational data model.

Potential future support:

```text
no_std
embedded systems
microcontrollers
edge devices
```

should be considered during API design.

---

# 52. Extensibility

The system must allow future modalities without redesign.

For example, if a future sensor detects:

```text
gravitational field
quantum state
novel chemical signature
biological marker
```

the system should be able to represent it without modifying the fundamental observation architecture.

---

# 53. Core Architectural Rule

The most important architectural rule is:

> **Do not build the intelligence into the sensor layer.**

`tpt-senses` should answer:

```text
What was measured?
What was observed?
Where?
When?
By what?
How reliable?
What evidence supports it?
```

`tpt-thought` should answer:

```text
What does it mean?
What should I believe?
What should I investigate?
What should I do?
```

`tpt-anima` should manage appropriate cognitive state and attention mechanisms.

`tpt-eve` should provide appropriate evaluation/verification.

# 59. Success Criteria

`tpt-senses` is successful when:

1. A new sensor can be integrated without modifying `tpt-thought`.
2. A new modality can be introduced without redesigning the core.
3. ROS can provide measurements without becoming a core dependency.
4. Existing TPT media repositories can contribute perception capabilities without being absorbed into `tpt-senses`.
5. Observations retain uncertainty and provenance.
6. Multiple sensors can be fused into a common observation.
7. Real and simulated sensors can use the same cognitive interface.
8. Internal system sensors can use the same observation model.
9. The architecture supports sensory capabilities beyond human perception.
10. `tpt-thought` can reason over observations without knowing the underlying hardware.

# 60. Final Principle

The fundamental abstraction of `tpt-senses` is not:

```text
SEE
HEAR
TOUCH
SMELL
TASTE
```

It is:

```text
                    MEASURE
                       ↓
                    PERCEIVE
                       ↓
                   OBSERVE
                       ↓
                   CORRELATE
                       ↓
                    INFORM
                       ↓
                   THINK
```

The system should therefore be capable of giving an intelligent agent senses that no human possesses.

A human might see visible light.

A TPT autonomous system might see:

```text
visible
infrared
ultraviolet
thermal
multispectral
```

A human might hear ordinary environmental sound.

A TPT system might perceive:

```text
infrasound
ultrasound
directional acoustic fields
machine vibration
```

A human cannot directly perceive ionising radiation.

A TPT system can.

The cognitive architecture does not need to care whether an observation corresponds to a biological sense.

It only needs to know:

> **Something has been measured, something has been perceived, and here is the evidence, uncertainty, provenance, time, and context required to reason about it.**

That is the role of `tpt-senses`.
